# Scientific Research Assistant: improvement roadmap

**Date:** 2026-10-20 · **Based on:** [`2026-10-20-skill-audit.md`](2026-10-20-skill-audit.md) · **Status: proposal, awaiting approval. Nothing here has been implemented.**

**Goal:** a local-first research assistant that combines Elicit-style evidence work (find, screen, extract with quotes, synthesise) with Julius-style analysis (load data, test, plot, report). It should be stricter than both about traceability: every claim maps to a source passage, and every number maps to code.

**Constraints:**
- Windows-friendly, standard-library core.
- Optional extras through `pip` only: pandas, scipy, statsmodels, matplotlib, pypdf, model2vec.
- Free APIs only. No GPU needed for anything below.

**Effort scale** (one developer working with Claude Code): **S** ≤ 1 day · **M** 2–4 days · **L** 1–2 weeks.

---

## 1. Principles

1. **Reliability before features.** Fix what gives wrong answers today (retrieval defaults, verdict wording) before adding new stages.
2. **Turn the project habits that worked into tooling.** The two finished papers succeeded because of `ANALYSIS_PLAN.md`, logged deviations, fixed seeds and a single `results.json`. Make these the default, not something to remember.
3. **Every artefact is checkable by a script:**
   - quotes against stored text;
   - numbers against `results.json`;
   - references against identifiers;
   - inputs against hashes.
4. **Fewer commands, one state file.** Claude should run `sra project status` and know where the project stands, in any session.
5. **Measure before integrating.** Retrieval changes ship only after they win on the frozen blind set (the rule in `evals/retrieval_blind/PLAN.md`).

## 3. Proposed architecture

```
                         ┌──────────────────────────────────────────┐
                         │  SKILL.md + references/  (rules, stages) │
                         └───────────────┬──────────────────────────┘
                                         │ Claude runs commands
┌────────────────────────────────────────▼─────────────────────────────────────────┐
│ sra project  (C1)   project.json: stage · decisions · artefacts+hashes · next     │
└──┬──────────────┬───────────────┬────────────────┬───────────────┬───────────────┘
   │ LITERATURE   │ EVIDENCE      │ DESIGN         │ ANALYSIS      │ WRITING
   ▼              ▼               ▼                ▼               ▼
 search/map    fulltext (+PDF)  ANALYSIS_PLAN    data profile    paper schema (C8)
 challenge     screen (A1)      template + lock  leakage(+time)  check-numbers (C3)
 related       extract (C2)     power (A5)       run+provenance  check-stats (C5)
 retrieval-    quote validator  stats reference  (C4)            verify-refs
 eval (F1)                      (C5)             sra.stats       report → md/tex/docx/pdf
   │              │                               figures (A4)     │
   └──────┬───────┘                                   │            │
          ▼                                           ▼            ▼
   library (A2): papers, abstracts,           results/results.json  Obsidian export
   full-text cache, quotes, read levels       results/provenance.json  (projects, papers,
   (keyed by DOI / arXiv ID)                  data/MANIFEST.json        dashboard)
```

Data contracts between the stages:
- **Papers:** the existing `Paper` model, stored in the library (A2).
- **Evidence:** one row per paper and column: `{value, quote, location, read_level}`. The quote is checked against the library's stored text.
- **Numbers:** `results/*.json` holds every reported number; `provenance.json` records how they were produced.
- **Decisions:** stored in `project.json` with dates, then rendered into reports and Obsidian.

Each validator stays a separate, testable function, and `sra project check` runs all of them.

| Rank | Item | Why first |

| 4 | **C4: analysis scaffold and run provenance** | Turns the habits behind both successful papers into defaults; makes the analysis half of the goal exist in the skill. About 3 days |

Expected effect: after these five, a project can be resumed from a single command. Every paper number has a code source, every evidence claim has a checked quote, and the novelty verdict reports its own measured miss rate.

## 5. The ideal end-to-end experience (after the core items)

> **Student:** "I want to write a paper on whether CVSS predicts real exploitation. Six weeks, laptop only."

1. **Project (C1).**
   - Claude runs `sra project init cvss-kev --question "…" --type replication`. Stage: `map`.
   - It asks once for missing constraints, then records the defaults.
2. **Map and discovery (2 min of searches, keys set).**
   - `map` and `challenge` run with `--project`. Claude reads the summary: 3 closest papers.
   - The verdict says: "close prior work found; in blind tests this search finds ~X% of known work".
   - Claude runs the printed web queries and adds two papers by DOI.
3. **Screen and extract (A1, C2).**
   - Claude screens 40 candidates against 3 criteria and keeps 9.
   - It fills an extraction table: data source, CVSS version, threshold, sensitivity, specificity, follow-up, and a limitation. Every cell has a quote.
   - `extract --check` confirms that all 63 quotes occur in the stored texts (two papers PDF-only, with page numbers).
4. **Gap and decision.**
   - The evidence ledger is built from the table.
   - Question: "Replicate Allodi & Massacci 2014 with KEV". Type: replication, `go`, with the closest work read in full.
   - The opportunity report renders; Obsidian is updated.
5. **Design (C4, C5, A5).**
   - `sra analysis init` writes the plan template.
   - Claude and the student fix H1–H6, α, Holm, effect sizes and robustness checks. The plan is hashed and locked.
6. **Data (C4, C6, C7).**
   - Downloads are recorded in `data/MANIFEST.json`.
   - `data profile` shows 409,838 CVEs and CVSS v3 missing for 2023+.
   - `leakage --feature-time-field` warns that current CVSS scores may postdate KEV listing. The warning becomes a limitation and a robustness idea.
7. **Analysis.**
   - `sra run analysis.py` writes `results.json` and `provenance.json`.
   - A deviation (complete separation) is logged in the plan with a date.
8. **Writing (C8, C3, C5).**
   - Claude drafts `paper.md`.
   - `check-numbers` flags 2 untraced values. Claude adds them to the analysis and reruns.
   - `check-stats` flags "not significant, so no effect". Claude rewords it.
   - `paper build` writes `.docx` and `.pdf` with verified references.
9. **Wrap-up.**
   - `sra project status` shows: stage `done`, all checks green, artefact hashes, and the Obsidian note updated.
   - Next session, "continue the CVSS paper" starts from `status`.

## 6. What we should explicitly NOT build

1. **Our own paper index or semantic search engine** over 100M+ papers. We use free APIs and, at most, local re-ranking of what they return.
2. **A web app, SaaS or real-time collaboration.** Claude Code, files, git and Obsidian are the interface.
3. **Model training or fine-tuning** of any research model inside the skill, including a custom relevance model.
4. **Automatic "novelty proof".** The ceiling stays at "medium", whatever retrieval improvements land.
5. **Automated test shopping:** running many tests or specifications and reporting the significant ones. Analyses follow the locked plan; extras are labelled exploratory.
6. **A full paper written without traced numbers and checked quotes**, or a "one-click paper" mode.
7. **Paid or closed sources** (Scopus, Web of Science, paid LLM APIs inside the toolkit), and **any access to paywalled full text** outside legitimate open access.
8. **Business-style data connectors or dashboards** (Snowflake, BigQuery, ads platforms) and notebooks. Julius itself is sunsetting Notebooks; plain scripts plus provenance serve research better.
9. **A heavy default dependency stack** (PyTorch, GROBID, Docker as requirements). Everything heavy stays optional.
10. **A full PRISMA systematic-review product.** A light screening log (A1) is enough for our users' gap-finding and replication work.
